# React porting decisions

Use this reference after the upstream compatibility checklist is known. It captures recurring traps; upstream remains authoritative for component-specific behavior.

## API mapping

- Keep the public `Gl*` naming convention. Export the component as the default export from its module and export public types explicitly from `packages/ui/src/index.ts`.
- Convert Vue props and defaults into strict TypeScript props and React defaults. Preserve meaningful distinctions among omitted values, `null`, empty strings, `0`, and empty children.
- Convert slots to typed React nodes or named render props only when their semantics differ. Convert emitted events to idiomatic callbacks and `v-model` pairs to controlled value/callback APIs.
- Forward a useful DOM or primitive handle through a typed ref when consumers need it. Do not expose Vue instance concepts.
- Prefer native HTML attributes when they already express the contract. Avoid duplicating or inventing ARIA.

## Base UI and polymorphism

- Use the closest Base UI primitive when it provides the required semantics. Alias imported primitives as `Base*` when that avoids confusion with the exported GitLab component.
- Prefer Base UI's `render` composition API over adding router-specific props. Keep component-owned state, classes, accessibility attributes, and event behavior when a custom element is rendered.
- Test composed router activation, not just its DOM shape. A default fallback such as `href="#"` must not call `preventDefault()` when `render` supplies the actual navigation element.
- Keep anchor semantics for links. Use native `disabled` only on elements that support it; otherwise combine `aria-disabled`, styling, focus policy, and event suppression according to upstream behavior.

## State, safety, and accessibility

- Make each supported state affect the same observable layers as upstream: rendered attributes, classes, interaction, accessible state, focus treatment, and visual styling.
- Preserve URL/protocol allowlists and other safety checks. For external links, preserve the documented target/`rel` behavior without weakening opener protection.
- Verify keyboard activation, focus visibility, disabled behavior, accessible name, and state announcements. Decorative icons must not add noise; meaningful icons need an accessible equivalent.
- CSS pseudo-element text can enter the accessible name in the browser. When an external-link glyph is generated by CSS, assert the semantic name or stable prefix rather than assuming exact visible text is the whole accessible name.

## Variants and CSS

- Model closed variants with `cva` and exported literal unions. Keep structural classes separate from consumer `className` merging.
- Translate Sass into colocated plain CSS using existing tokens and utilities. Inspect mixin definitions and transitive global styles before replacing them; do not approximate a hidden behavior by appearance alone.
- Cover hover, active, focus-visible, disabled, dark theme, forced colors, reduced motion, and responsive behavior only where upstream or shared foundations support them.
- Import component CSS from `packages/styles/src/components.css`. Regenerate `packages/styles/dist` with the styles package build; never hand-edit generated output.

## Dependencies and provenance

- Reuse existing React primitives, icons, tokens, and styles before adding dependencies. Put dependencies in the package that consumes them, use `workspace:^` for internal packages, and update Vite externals when a runtime dependency must remain external.
- Add a concise comment to substantially adapted files, for example:

```text
Ported from packages/gitlab-ui/src/components/base/<component>/<file> in
gitlab-org/gitlab-services/design.gitlab.com.
```

- Preserve applicable upstream copyright and license headers.
- Do not add a TODO for an omitted upstream behavior unless the boundary, reason, and expected follow-up are explicit and testable.
